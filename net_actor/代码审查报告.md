## 一、架构概览

### 模块分层

| 层次 | 关键类 | 职责 |
|------|--------|------|
| I/O 层 | `EventLoop` / `Epollor` / `Poller` | epoll 事件循环，fd↔Connection 映射 |
| 连接层 | `IConnection` / `ConnectionBase` / `Connection` / `Connector` / `Acceptor` | 读写逻辑、accept、非阻塞 connect |
| 消息层 | `Message.h` / `Buffer.h` / `MessageBuffer.h` | ActorMessage、发送缓冲、共享零拷贝 buffer |
| 调度层 | `ActorSystem` / `Actor` | Actor 注册/调度、邮箱、工作线程池 |
| 协程层 | `Coroutine.h` | CallAwaiter / ClusterCallAwaiter / SleepAwaiter |
| 定时器 | `Timer.h` / `Timer.cc` | 最小堆定时器，独立线程 |
| 集群扩展 | `ClusterProxy.h` / `ClusterProxy.cc` | 跨进程 RPC、TCP 集群传输 |
| 入口层 | `TcpServer` / `TcpClient` / `EventLoopThreadPool` | 组装、主从 Reactor |

### 线程模型

- 主线程：保活或 stdin
- epoll loop 线程（主 Reactor）：accept / read / write
- SubReactor 线程池（可选）：分担已建立连接的 I/O
- Actor worker 线程池：业务逻辑串行处理
- Timer 线程：定时器调度

### 关键并发原语

- `SpinLock` + `LockGuard`：保护各类映射表
- `SpinLockQueue<T>`：邮箱、就绪队列、发送队列
- `std::atomic<bool> scheduled_`：Actor 调度去重
- `std::condition_variable cv_`：唤醒 worker

## 二、P0 严重问题（UAF / 死锁 / 数据丢失）

### P0-1  Actor 裸指针跨锁使用 — UAF 风险

**位置**：[ActorSystem.cc:137-157](ActorSystem.cc#L137-L157) `Send`、[ActorSystem.cc:484-497](ActorSystem.cc#L484-L497) `workerLoop`

**问题**：
```cpp
void ActorSystem::Send(uint32_t actorId, ActorMessage&& msg)
{
    Actor* actor = nullptr;
    {
        LockGuard<SpinLock> lock(actorsLock_);
        auto it = actors_.find(actorId);
        if (it == actors_.end()) return;
        actor = it->second.get();   // 锁内取裸指针
    }
    // 锁外：actor 可能已被 UnregisterActor 析构
    actor->PushMessage(std::move(msg));
    bool expected = false;
    if (actor->scheduled_.compare_exchange_strong(expected, true)) {
        readyQueue_.push(actorId);
        cv_.notify_one();
    }
}
```

`workerLoop` 同样：锁外调 `actor->ProcessOne()`。

`UnregisterActor` 路径真实存在（[ClusterProxy.cc:319-321](ClusterProxy.cc#L319-L321) `TcpClusterTransport::~TcpClusterTransport` 调用），所以这是真实 UAF。

**修复建议**：
- `actors_` 改用 `std::unordered_map<uint32_t, std::shared_ptr<Actor>>`
- `Send` / `workerLoop` 持有 `shared_ptr` 副本，保证生命周期

---

### P0-2  `ActorSystem::Stop` Phase 3 持锁调 ProcessOne — 死锁

**位置**：[ActorSystem.cc:49-68](ActorSystem.cc#L49-L68)

**问题**：
```cpp
LockGuard<SpinLock> lock(actorsLock_);
for (auto& [id, actor] : actors_) {
    while (!actor->IsMailboxEmpty() && drained < 64) {
        actor->ProcessOne();  // 业务 OnCoroutineMessage → SendToActor → Send → 再次获取 actorsLock_
    }
}
```

`SpinLock` 不可重入，业务代码回调 `Send` 时必然死锁。

**修复建议**：锁内只拷贝 actor 列表（`std::vector<Actor*>` 或 `std::vector<std::shared_ptr<Actor>>`），释放锁后再 `ProcessOne`。

### P0-3  不支持优雅关停 — 资源管理混乱

**位置**：
- [Acceptor.cc:118](Acceptor.cc#L118) `loop_->AddConnection(this)`
- [Connector.cc:125](Connector.cc#L125) `loop_->AddConnection(this)`
- [TcpServer.cc:60-62](TcpServer.cc#L60-L62) `while(true) { usleep(...); }` 死循环
- [TcpClient.cc:42-53](TcpClient.cc#L42-L53) `while(true) { ... }` 死循环

**问题**：

`Acceptor` 与 `Connector` 把自身加入 `mapConn_`，但它们由外部 `new` 创建（TcpServer/TcpClient/TcpClusterTransport 持有指针）。[EventLoop.cc:22 注释](EventLoop.cc#L22) 声称「Acceptor/Connector 不在 mapConn_ 中」，与实际代码矛盾。

当前代码依赖 `while(true)` 死循环保持程序运行，**不支持优雅关停**：
- 若程序正常退出，`TcpServer`/`TcpClient` 析构 → EventLoop 析构时 `delete pConn` 会把 Acceptor/Connector 也 delete
- 同时 `TcpServer::acceptor_` 仍持有指针 → 潜在 double-free（虽然当前死循环不会触发）
- `TcpClusterTransport` 析构时未 delete `acceptor_` → 若 EventLoop 先析构则 OK，否则泄漏

**修复建议**：
- 明确所有权：`Acceptor`/`Connector` 不调用 `AddConnection`，或 EventLoop 只管理 `Connection` 类型
- 添加 `TcpServer::Stop()` / `TcpClient::Stop()` 方法支持优雅关停
- `TcpClusterTransport` 析构时显式释放 `acceptor_` 和所有 Connector

---

### P0-4  `Actor::SendToNetwork` 返回的 Connection 裸指针锁外使用 — UAF

**位置**：[Actor.cc:222-237](Actor.cc#L222-L237)

**问题**：
```cpp
void Actor::SendToNetwork(int fd, const char* pData, int nLen)
{
    auto* loop = system_->GetEventLoopByFd(fd);
    if (loop) {
        auto* pConn = loop->GetConnection(fd);  // 持 connSpinLock_ 返回裸指针
        if (pConn) {
            pConn->Send(pData, nLen);            // 锁外，loop 线程可能 RemoveConnection 已 delete
        }
    }
}
```

worker 线程与 loop 线程并发时真实触发：
1. worker 调 `GetConnection` 拿到裸指针
2. loop 线程 `RemoveConnection` → `delete pConn`
3. worker 调 `pConn->Send(...)` → UAF

**修复建议**：
- `Connection` 改 `shared_ptr<IConnection>`，`GetConnection` 返回 `shared_ptr`
- 或 `Send` 接口完全异步：只把数据投递到 loop 线程的 pending task，不在 worker 线程直接访问 Connection

### P0-5  ClusterGatewayActor 大包数据直接丢失

**位置**：[ClusterProxy.cc:224-241](ClusterProxy.cc#L224-L241)

**问题**：
```cpp
case MsgType::NetworkRecv: {
    auto& buf = recvBuffers_[msg.fd];
    buf.append(msg.data);   // 忽略了 sharedBuf！
    ...
}
```

但 [ConnectionBase.cc:139](ConnectionBase.cc#L139) 用 `ActorMessage::Make`，`>= kBufferThreshold`（1024 字节）走 `sharedBuf`，`data` 字段为空。集群 TCP 单包超过 1KB 时**整包丢失**。

同样问题见 [ClusterProxy.cc:32](ClusterProxy.cc#L32) `pkt.data = msg.data`（ClusterProxy 转发出方向）。

**修复建议**：统一用 `msg.CopyToString()` 或 `buf.append(msg.Data(), msg.Size())`。

### P0-6  TcpClusterTransport 资源泄漏 / 悬空

**位置**：
- [ClusterProxy.cc:337](ClusterProxy.cc#L337) `acceptor_ = new Acceptor(...)`
- [ClusterProxy.cc:346](ClusterProxy.cc#L346) `new Connector(...)`（未保存指针）

**问题**：
```cpp
void TcpClusterTransport::ConnectToNode(...)
{
    auto* connector = new Connector(loop_, port, ip, gatewayActorId_);
    int fd = connector->GetFd();
    // connector 指针未保存！
    ...
}

TcpClusterTransport::~TcpClusterTransport()
{
    if (sys_ && gatewayActorId_ > 0) {
        sys_->UnregisterActor(gatewayActorId_);
    }
    // 既没 delete acceptor_，也没 delete ConnectToNode 创建的 Connector
}
```

依赖 EventLoop 析构时通过 `mapConn_` 兜底 delete。若 EventLoop 先析构则 OK；若 TcpClusterTransport 先析构且 EventLoop 仍存活，Connector 指针彻底泄漏（acceptor_ 也未 delete）。

**修复建议**：
- `TcpClusterTransport` 保存所有 Connector 指针（`std::vector<std::unique_ptr<Connector>>`）
- 析构时显式释放 `acceptor_` 和所有 Connector
- 或统一改用 `shared_ptr` 链

## 三、P1 中等问题（功能缺陷 / 较高概率触发）

### P1-1  Connector 连接失败不通知 ownerActor

**位置**：[Connector.cc:41-53](Connector.cc#L41-L53)

**问题**：连接失败直接 `RemoveEvent + close`，不发 `Disconnected` 消息。业务层 `co_await Call` 或等连接事件会永久阻塞直到超时。

**修复建议**：失败时补发 `MsgType::Disconnected` 给 `ownerActorId_`。

---

### P1-2  `ActorSystem::Stop` 未清理协程帧

**位置**：[ActorSystem.cc:81-90](ActorSystem.cc#L81-L90)

**问题**：Phase 5 清理 name/link 映射，但未调用 `actor->DestroyAllCoroutines()`。挂起在 `co_await Call/Sleep` 的协程帧泄漏（[Actor.cc:178-189](Actor.cc#L178-L189) 提供了接口却没被调用）。

**修复建议**：Phase 5 之前遍历 actors 调用 `DestroyAllCoroutines()`。

---

### P1-3  `ClusterPacketCodec::Decode` 对 bodyLen=0 永久阻塞

**位置**：[ClusterProxy.cc:172-204](ClusterProxy.cc#L172-L204)

**问题**：`bodyLen=0` 通过校验（未检查下界），但后续 `ReadStr16` 立刻返回 false，Decode 返回 0，调用方 [ClusterProxy.cc:233](ClusterProxy.cc#L233) `break` 等待后续数据。恶意/异常包导致该 fd 永久卡死。

**修复建议**：`bodyLen < 最小合法长度`（如 14 字节：四个 Str16 头 + U32 + U8 + 空 Str32）时返回 `-1` 让上层丢弃连接。

---

### P1-4  TcpServer/TcpClient 成员声明顺序导致析构竞态

**位置**：[TcpClient.h:29-34](TcpClient.h#L29-L34)、[TcpServer.h:36-41](TcpServer.h#L36-L41)

**问题**：
```cpp
class TcpClient {
    EventLoop loop_;          // 先声明 → 后析构
    ActorSystem actorSystem_; // 后声明 → 先析构
    IConnection* conn_;
};
```

析构顺序：`conn_ → actorSystem_ → loop_`。

`actorSystem_` 先析构（调用 `Stop()`）时，`loop_` 的 epoll 线程**仍在运行**：
- HandleRead 可能调用 `actorSystem_->SendByFd()` → 访问已析构的 ActorSystem → UAF
- 或 `loop_` 线程正在执行 pending task 访问 ActorSystem

**修复建议**：
- 添加显式 `Stop()` 方法控制关停顺序：**先停 EventLoop（停止 I/O），再停 ActorSystem**
- 或调整成员声明顺序为 `actorSystem_` 在前、`loop_` 在后（让 `loop_` 先析构）

---

### P1-5  Connector 析构不 RemoveConnection

**位置**：[Connector.cc:20-25](Connector.cc#L20-L25)

**问题**：只 `close(socket_)`，`mapConn_` 残留指针。fd 复用后 `GetConnection` 返回悬空指针。

**修复建议**：close 前调用 `loop_->RemoveConnection(fd)`。

---

### P1-6  `GetActorCount() const` 需要 `const_cast`

**位置**：[ActorSystem.cc:304-308](ActorSystem.cc#L304-L308)

**问题**：
```cpp
size_t ActorSystem::GetActorCount() const
{
    LockGuard<SpinLock> lock(const_cast<SpinLock&>(actorsLock_));
    return actors_.size();
}
```

`actorsLock_` 非 mutable，const 方法 const_cast 是设计缺陷。

**修复建议**：`actorsLock_`、`fdMapLock_`、`nameLock_`、`linkLock_`、`transportLock_`、`pendingLock_`、`connLock_`、`nodesLock_`、`cbSpinLock_`、`connSpinLock_`、`pendingLock_` 全部声明为 `mutable`。

## 五、修复优先级与根因分析

### 优先级矩阵

| 优先级 | 问题编号 | 建议批次 |
|--------|----------|----------|
| **P0** | P0-1 / P0-2 / P0-3 / P0-4 / P0-5 / P0-6 | 第一批：统一生命周期管理 + 支持优雅关停 |
| **P1** | P1-1 ~ P1-6 | 第二批：功能缺陷与健壮性 |
| **P2** | P2-1 ~ P2-10 | 按需优化 |

### 根因分析

**核心根因**：Actor 与 Connection 的所有权管理混乱 + 不支持优雅关停
- 裸指针 + 跨锁使用 + EventLoop 与外部双重管理
- 依赖死循环运行，缺少 Stop 机制
- 一次性消除 P0-1 / P0-3 / P0-4 / P2-3 等多个 UAF 类问题

**建议方案**：

1. **Actor 生命周期**：`actors_` 改为 `unordered_map<uint32_t, shared_ptr<Actor>>`
   - `Send` / `workerLoop` 持有副本
   - `UnregisterActor` 仅从 map 移除，引用计数归零后自然析构

2. **Connection 生命周期**：`mapConn_` 改为 `unordered_map<int, shared_ptr<IConnection>>`
   - `GetConnection` 返回 `shared_ptr`
   - `RemoveConnection` 仅从 map 移除，不立即 delete

3. **关停顺序**：
   - 添加 `TcpServer::Stop()` / `TcpClient::Stop()` 方法支持优雅关停
   - 关停顺序：**先停 EventLoop（停止 I/O 投递）→ 再停 ActorSystem（排空业务）**
   - 当前成员声明顺序（loop_ 在前）导致析构时 ActorSystem 先停但 loop_ 还在跑，存在竞态

4. **消息数据统一访问**：
   - 所有从 `ActorMessage` 取数据的地方强制用 `Data()/Size()` 或 `CopyToString()`
   - 禁止直接访问 `msg.data` 字段（小包专用，大包为空）

5. **协议健壮性**：
   - `Decode` 对 bodyLen 做上下界校验
   - 异常包返回错误码，上层主动断开连接

### 修复工作量预估

| 批次 | 工作量 | 风险 |
|------|--------|------|
| 第一批（P0） | 3-5 天 | 高：涉及核心数据结构改造，需充分回归测试 |
| 第二批（P1） | 2-3 天 | 中：接口与析构顺序调整 |
| 第三批（P2） | 1-2 天 | 低：性能与可读性优化 |

### 验证建议

- 编写 UAF 检测用例：高频注册/注销 Actor + 并发 Send
- 编写关停测试：Stop 期间持续 Send，验证不死锁
- 集群大包测试：单包 > 1KB 验证零丢失
- 协议模糊测试：构造异常 bodyLen 验证不卡死

### 6.2 修复详情

#### F-01 `ConnectionBase::Send` 跨线程 lambda 捕获 `this` → UAF

**对应原报告**：P2-3

**根因**：`Send` 的 slow-path（大包与小包两条）通过 `RunInLoop` 投递 lambda，lambda 捕获 `this` 并调用 `sendInLoop`（间接访问 `outputBuffer_`）。若任务执行前 Connection 已被 `RemoveConnection` 析构，lambda 访问 `this` 即 UAF。

**修复方案**：lambda 不再捕获 `this`，改为捕获 `EventLoop* loop`（裸指针，由 EventLoop 生命周期保证）+ `fd`。lambda 内通过 `loop->GetConnection(fd)` 重新取 `shared_ptr<IConnection>`，持有副本期间不会被析构。

**关键代码**：
```cpp
loop_->RunInLoop([loop, fd, buf = std::move(buf)]() mutable {
    auto conn = loop->GetConnection(fd);
    if (!conn) return;
    conn->Send(buf->Data(), static_cast<int>(buf->Size()));
});
```

**验证要点**：高频 connect/disconnect + 同时 Send 大包，验证无 UAF / ASAN 无报错。

#### F-02 `TcpClusterTransport` 未保存 `Connector` 指针 + `acceptor_` 裸指针

**对应原报告**：P0-6

**根因**：
1. `ConnectToNode` 用 `new Connector(...)` 创建但未保存指针，仅保存 `fd`。依赖 EventLoop 析构时通过 `mapConn_` 兜底 delete，但 `TcpClusterTransport` 析构时 EventLoop 可能仍存活 → Connector 彻底泄漏。
2. `acceptor_` 是裸指针，析构未 delete。

**修复方案**：
- `ClusterProxy.h` 增加 `std::vector<std::unique_ptr<Connector>> connectors_;` 成员
- `acceptor_` 改为 `std::unique_ptr<Acceptor>`
- `ConnectToNode` 用 `make_unique<Connector>`，emplace 到 `connectors_`
- `~TcpClusterTransport` 先清空 `connectors_` 和 reset `acceptor_`，再 `UnregisterActor`
- `Connector` 析构函数增加 `loop_->RemoveConnection(socket_)` 清理 `mapConnRaw_` 映射
- `Connector::HandleWrite` 连接失败路径增加 `loop_->RemoveConnection(fd)` 避免映射残留

**验证要点**：反复 `ConnectToNode` + `~TcpClusterTransport`，Valgrind/ASAN 验证无泄漏、无 UAF。

#### F-03 `RegisterNodeFd` / `OnNodeDisconnected` 双连接竞态

**对应原报告**：新增（集群双向连接场景）

**根因**：集群节点 A↔B 双向主动连接时，可能同时建立两条连接（A→B 和 B→A），但只保留一条。原 `RegisterNodeFd` 直接覆盖 `nodeToFd_[nodeId]`，被覆盖的旧 fd 的 `fdToNode_` 残留；`OnNodeDisconnected` 直接 `erase nodeToFd_[nodeId]`，但若该 nodeId 已被新 fd 替换，会误擦新连接的映射。

**修复方案**：
- `RegisterNodeFd`：若 `nodeId` 已映射到不同 fd，先清理旧 fd 的 `fdToNode_` 条目再覆盖
- `OnNodeDisconnected`：增加 `wasActiveFd` 标志，只有当 `nodeToFd_[nodeId]` 仍指向当前 fd 时才 erase

**关键代码**：
```cpp
void TcpClusterTransport::RegisterNodeFd(int fd, const std::string& nodeId) {
    bool wasActiveFd = false;
    {
        LockGuard<SpinLock> lock(nodesLock_);
        auto it = nodeToFd_.find(nodeId);
        if (it != nodeToFd_.end() && it->second != fd) {
            fdToNode_.erase(it->second);  // 清理旧 fd 反向映射
            wasActiveFd = false;
        }
        nodeToFd_[nodeId] = fd;
        fdToNode_[fd] = nodeId;
    }
}

void TcpClusterTransport::OnNodeDisconnected(int fd) {
    bool wasActiveFd = false;
    {
        LockGuard<SpinLock> lock(nodesLock_);
        auto it = fdToNode_.find(fd);
        if (it != fdToNode_.end()) {
            std::string nodeId = it->second;
            auto nit = nodeToFd_.find(nodeId);
            if (nit != nodeToFd_.end() && nit->second == fd) {
                nodeToFd_.erase(nit);
                wasActiveFd = true;
            }
            fdToNode_.erase(it);
        }
    }
    if (wasActiveFd) {
        NotifyActorDown(nodeId);  // 仅当 active fd 断开才通知
    }
}
```

**验证要点**：两个节点同时互连，验证最终只保留一条连接，断开后 `NotifyActorDown` 仅触发一次。

#### F-04 `EchoServerActor` / `EchoClientActor` 直接用 `msg.data` → 大包丢数据

**对应原报告**：P0-5（Echo 路径部分）

**根因**：`EchoServerActor::OnCoroutineMessage` 用 `msg.data.c_str()` / `msg.data.size()` 访问数据。但 `ActorMessage::Make` 在 `nLen >= kBufferThreshold`（1024 字节）时走 `sharedBuf` 路径，`data` 字段为空。Echo 服务回传超过 1KB 的数据时整包丢失。

**修复方案**：统一用 `msg.Data()` / `msg.Size()`（内部根据 `sharedBuf` 是否为空自动选择），或 `msg.CopyToString()`。

```cpp
// TcpServer.cc - EchoServerActor
SendToNetwork(msg.fd, msg.Data(), static_cast<int>(msg.Size()));

// TcpClient.cc - EchoClientActor
std::string data = msg.CopyToString();
```

**验证要点**：单包 2KB / 10KB / 1MB 的 echo 测试，验证收发一致。

#### F-05 `ClusterPacketCodec::Decode` 对 `bodyLen` 无下界校验

**对应原报告**：P1-3

**根因**：`bodyLen=0` 或过小通过校验（未检查下界），后续 `ReadStr16` 立刻返回 false，Decode 返回 0，调用方 `break` 等待后续数据。恶意/异常包导致该 fd 永久卡死。

**修复方案**：
- `Decode` 返回类型从 `size_t` 改为 `ssize_t`（-1 = 错误，0 = 需要更多数据，>0 = 消费字节数）
- 新增 `static constexpr size_t kMinBodyLen = 2 + 2 + 2 + 2 + 4 + 1 + 4;`（17 字节：四个 Str16 头 + U32 traceId + U8 msgType + 空 Str32 payload）
- `bodyLen > buf.size()` 或 `bodyLen < kMinBodyLen` 时返回 -1

**验证要点**：构造 bodyLen=0、bodyLen=1、bodyLen=kMinBodyLen-1 的异常包，验证连接被立即断开。

#### F-06 `ClusterGatewayActor` NetworkRecv 未处理 `consumed < 0`

**对应原报告**：P0-5 衍生

**根因**：`Decode` 返回 -1（错误包）后，原代码按 `consumed == 0` 处理，`break` 等待更多数据。错误包永久累积在 `recvBuffers_[fd]`，内存泄漏 + fd 卡死。

**修复方案**：`consumed < 0` 时：
1. 清空 `recvBuffers_[fd]`
2. 调用 `OnNodeDisconnected(fd)` 清理映射
3. `loop_->RemoveConnection(fd)` + `RemoveEvent(fd)` 关闭连接
4. `co_return` 终止协程

**关键代码**：
```cpp
ssize_t consumed = ClusterPacketCodec::Decode(buf, pkt);
if (consumed < 0) {
    std::cerr << "[Gateway] Decode error, closing fd=" << msg.fd << std::endl;
    recvBuffers_.erase(msg.fd);
    OnNodeDisconnected(msg.fd);
    loop_->RemoveConnection(msg.fd);
    loop_->RemoveEvent(msg.fd);
    close(msg.fd);
    co_return;
}
if (consumed == 0) break;
buf.erase(0, consumed);
```

**验证要点**：发送畸形包后验证连接被关闭、内存不泄漏、其他节点不受影响。

#### F-07 协程 `unhandled_exception` 调用 `std::terminate`

**对应原报告**：新增

**根因**：`Coroutine.h` 中 `promise_type::unhandled_exception` 调用 `std::terminate()`。任意 Actor 协程抛出未捕获异常（如 `std::bad_alloc`、业务代码 throw、第三方库异常）会直接拖垮整个进程。

**修复方案**：捕获异常并打印日志后吞掉（协程中止，不影响其他 Actor 与 worker 线程）。

```cpp
void unhandled_exception() {
    try {
        std::rethrow_exception(std::current_exception());
    } catch (const std::exception& e) {
        std::cerr << "[Actor] coroutine unhandled exception: " << e.what() << std::endl;
    } catch (...) {
        std::cerr << "[Actor] coroutine unknown exception" << std::endl;
    }
}
```

**验证要点**：在 Actor 协程中故意 `throw std::runtime_error("test")`，验证进程不崩溃、日志有记录、其他 Actor 正常工作。

#### F-08 不支持优雅关停 + 成员声明顺序导致析构竞态

**对应原报告**：P0-3 / P1-4

**根因**：
1. `TcpServer::Start` / `TcpClient::Start` 用 `while(true)` 死循环保活，无 `Stop()` 方法。
2. 成员声明顺序 `EventLoop loop_` 在前、`ActorSystem actorSystem_` 在后 → 析构时 `actorSystem_` 先析构，但 `loop_` 的 epoll 线程仍在跑，HandleRead 可能访问已析构的 ActorSystem → UAF。

**修复方案**：
1. 成员声明顺序调整为 `ActorSystem actorSystem_` 在前、`EventLoop loop_` 在后（先析构 loop_，I/O 先停）
2. 新增 `std::atomic<bool> running_{false};` 成员，`while(running_.load())` 替代 `while(true)`
3. 新增 `Stop()` 方法，关停顺序：**running_=false → loop_.Stop() → subReactorPool_.Stop()（如有）→ actorSystem_.Stop() → acceptor_/connector_.reset()**
4. `acceptor_` / `connector_` 改为 `std::unique_ptr` 管理

**关键代码**（TcpServer 为例）：
```cpp
// TcpServer.h
class TcpServer {
private:
    ActorSystem actorSystem_;                  // 先声明 → 后析构
    EventLoop loop_;
    EventLoopThreadPool subReactorPool_;
    std::unique_ptr<Acceptor> acceptor_;
    uint32_t serverActorId_ = 0;
    std::atomic<bool> running_{false};
public:
    void Start(int port, int subReactorNum = 0, int workerCount = 4);
    void Stop();
};

// TcpServer.cc
void TcpServer::Stop() {
    running_.store(false);
    loop_.Stop();
    if (subReactorPool_.Enabled()) subReactorPool_.Stop();
    actorSystem_.Stop();
    acceptor_.reset();
}
```

TcpClient 同样处理（无 SubReactorPool，其余一致）。

**验证要点**：
- 在 Stop 期间持续 Send，验证不死锁、不 UAF
- 多次 Start/Stop 循环，验证无资源泄漏
- ASAN 下运行 Stop 流程，验证无报错

#### F-09 `Acceptor::HandleAccept` 新连接注册 `EPOLL_EVENTS_RW`

**对应原报告**：新增

**根因**：新连接注册 `EPOLL_EVENTS_RW`（读+写），但连接刚建立时没有数据要写，EPOLLOUT 立即触发空跑 `HandleWrite`。虽然 `HandleWrite` 检查 `outputBuffer_.Empty()` 后直接返回，但每次新连接都触发一次无意义的 epoll 通知 + 回调。

**修复方案**：新连接初始只注册 `EPOLL_EVENTS_R`（仅读）。业务层调 `Send()` 时会自动加上 EPOLLOUT。

```cpp
// Acceptor.cc - HandleAccept
targetLoop->AddEvent(clientFd, EPOLL_EVENTS_R, [targetLoop](int fd, uint32_t event) {
    ...
});
```

**验证要点**：新连接建立后立即抓 `epoll_wait` 返回的事件，验证无 EPOLLOUT 触发。

#### F-10 `LinkActor` 未校验 watcher/target 存在

**对应原报告**：P2-5

**根因**：`LinkActor` 仅查 self-link，未查 watcher/target 是否已注册。后续 `notifyActorDown` 会向不存在的 watcher `Send` 触发噪音日志。

**修复方案**：在 link 前校验 `actors_.find(watcherId)` 和 `actors_.find(targetId)`。为避免与 `linkLock_` 死锁，先在 `actorsLock_` 内拷贝验证结果，释放 `actorsLock_` 后再获取 `linkLock_`。

**关键代码**：
```cpp
bool ActorSystem::LinkActor(uint32_t watcherId, uint32_t targetId) {
    {
        LockGuard<SpinLock> lock(actorsLock_);
        if (watcherId == targetId) return false;
        if (actors_.find(watcherId) == actors_.end()) {
            std::cerr << "[ActorSystem] LinkActor watcher not found: " << watcherId << std::endl;
            return false;
        }
        if (actors_.find(targetId) == actors_.end()) {
            std::cerr << "[ActorSystem] LinkActor target not found: " << targetId << std::endl;
            return false;
        }
    }
    LockGuard<SpinLock> lock(linkLock_);
    links_[watcherId].insert(targetId);
    return true;
}
```

**验证要点**：传入不存在的 actorId，验证返回 false 且无后续噪音日志。

#### F-11 `ClusterProxy::OnCoroutineMessage` 收到空 `senderName` 不告警
