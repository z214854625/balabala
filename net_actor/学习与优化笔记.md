## 一、整体架构与代码导读

整个框架是一个 **Actor 模型 + C++20 协程** 的网络服务框架，对标 Skynet 的服务协程模型。

### 线程模型

```
┌─────────────────┐   ┌──────────────────────────────────┐
│  EventLoop线程  │   │      ActorSystem Worker线程池      │
│  (单线程 epoll) │   │   (workerLoop × N，处理业务)        │
│   I/O 读写      │──▶│   ProcessOne → OnMessage → 协程    │
└─────────────────┘   └──────────────────────────────────┘
        ▲                          ▲
        │                          │
┌────────────────┐         ┌─────────────────┐
│ TimerManager   │         │ ClusterTransport│
│ 独立线程+最小堆 │         │ (跨进程TCP通信) │
└────────────────┘         └─────────────────┘
```

### 核心组件

- **EventLoop**：1 个 epoll 线程，承担所有 I/O；读到数据后投递给 Actor
- **ActorSystem**：N 个 worker 线程从就绪队列拉 Actor 处理消息
- **Actor**：拥有独立邮箱，消息串行处理，原 `CoroutineActor` 已合并进来
- **TimerManager**：单独线程 + 最小堆，处理 `Sleep`/`SetTimeout`/`SetInterval`
- **ClusterProxy / IClusterTransport**：跨进程消息透传

## 三、Actor 模式核心逻辑

### 1. 邮箱（双队列，P3 优化）

`Actor` 内部维护两个 `SpinLockQueue`：
- `priorityMailbox_`：高优先级
- `normalMailbox_`：普通

`PushMessage` 根据 `msg.priority` 路由，`ProcessOne` 优先弹出高优先级。同时做了：
- 高水位告警 (`mailboxHighWaterMark_`)
- 指标统计（耗时、最大邮箱大小，P2 A.9）

### 2. 调度（ActorSystem）

每个 Actor 有一个原子标记 `scheduled_`，避免就绪队列中重复出现。

`Send()` 流程：取出 Actor → `PushMessage` → CAS 设置 `scheduled_` → 入就绪队列 → `cv_.notify_one()`。

`workerLoop()`：
1. 从就绪队列 `pop` 一个 actorId
2. 批量处理至多 64 条消息（防止饥饿）
3. 用 `try/catch` 包裹，单条消息异常不影响 worker 存活（P0）
4. 处理完后，邮箱非空则重新入队，邮箱空则清 `scheduled_` 并做**双重检查**（解决 push 和 scheduled 设置之间的竞态）

#### `scheduled_.store(false)` 与双重检查的必要性

```cpp
if (!actor->IsMailboxEmpty()) {
    readyQueue_.push(actorId);
    cv_.notify_one();
} else {
    actor->scheduled_.store(false);
    // 双重检查：防止在取消标记和检查之间有新消息到达
    if (!actor->IsMailboxEmpty()) {
        bool exp = false;
        if (actor->scheduled_.compare_exchange_strong(exp, true)) {
            readyQueue_.push(actorId);
            cv_.notify_one();
        }
    }
}
```

如果不写 `store(false)`：worker 处理完后退出，但 `scheduled_` 仍为 true。后续 Send 触发 CAS 失败 → **不会入就绪队列** → Actor 永远不会被处理 → "丢失唤醒"bug。

双重检查解决了 `IsMailboxEmpty` 检查与 `store(false)` 之间的窗口竞态。

### 3. 消息分发（关键，`Actor::OnMessage`）

```cpp
if (msg.isResponse && msg.sessionId > 0) {
    ResumeWaiting(msg.sessionId, std::move(msg));  // 唤醒挂起的协程
} else {
    OnCoroutineMessage(std::move(msg));             // 新消息 → 启动新协程
}
```

这是把 Actor 模型和协程串起来的核心枢纽。

### 4. 其他能力

- **fd→actorId 绑定**：网络数据按 fd 路由到对应 Actor
- **命名服务**：`RegisterName`/`FindActor`/`SendByName`（P1）
- **Link 监控**：`LinkActor` 注册 watcher，被监控 Actor 注销时 `notifyActorDown` 发送 `ActorDown` 消息（P2）
- **跨进程集群**：`SendToRemote` 走 `IClusterTransport`，封装为 `ClusterPacket`（含 sourceNodeId / sourceActorName 做回程路由）
- **优雅关停**：Stop 五阶段——停定时器 → 停 worker → 排空邮箱 → 警告未处理消息 → 清名字/Link 映射
- **指标**：`ActorMetrics`（处理数、累计/最大耗时、最大邮箱、优先级数）

### `workerLoop` 中的 try/catch 性能影响

C++ 现代异常实现是 **table-based zero-cost exception**：
- **不抛异常时**：几乎为 0 成本（编译期登记）
- **抛异常时**：贵（栈展开），但属于"已经出错"场景

`workerLoop` 的 try 包了一整批消息（≤64 条），不是每条一个 try——即使每秒处理百万消息，try 的开销也几乎不存在。**这是教科书级的合理用法**。

## 四、协程逻辑（Skynet 风格服务协程）

### 1. 返回类型 `ActorTask`

```cpp
struct promise_type {
    std::suspend_never initial_suspend();   // 立刻执行
    std::suspend_never final_suspend();     // 完成自动销毁帧
    void return_void(); ...
};
```

**Fire-and-forget**：调用方不持有 `coroutine_handle`，协程帧生命周期由挂起点和 `final_suspend` 管理。

### 2. 协程入口

`OnCoroutineMessage(ActorMessage msg)` 是用户重写的虚函数，**参数按值传递**——因为协程可能挂起，原 `ProcessOne()` 的栈引用会失效。

### 3. 三种 Awaiter

| Awaiter | 触发 | 挂起时 | 何时恢复 |
|---|---|---|---|
| `CallAwaiter` | `co_await Call(id, msg)` | AllocSession + StoreWaiting + SendToActor | 目标 Actor `Respond` 回发 isResponse=true 的消息 → `OnMessage` → `ResumeWaiting` |
| `ClusterCallAwaiter` | `co_await ClusterCall(node, name, msg)` | 同上，但用 `SendToRemote` | 远端 `RespondRemote` → TCP 返回 → ClusterGatewayActor 解码 → `SendByName` 路由 → `ResumeWaiting` |
| `SleepAwaiter` | `co_await Sleep(ms)` | 注册等待 + `TimerManager.SetTimeout` 投递唤醒消息 | 定时器到期 → `ResumeWaiting` |

### 4. 协程的"挂起-恢复"全流程

```
Actor A 在 worker 线程中：
  OnCoroutineMessage(msg)
    └─ co_await Call(B, req)              // CallAwaiter
         ├─ AllocSession → 100
         ├─ waitMap_[100] = handle        // StoreWaiting
         ├─ Send(B, req{sessionId=100})
         └─ 协程挂起 → worker线程返回 → 处理其他Actor

… Actor B 在另一个 worker 线程：
  OnCoroutineMessage(req)
    └─ RespondToCall(req, resp)
         └─ resp.isResponse=true, sessionId=100 → Send(A, resp)

… Actor A 再次被调度：
  ProcessOne → OnMessage(resp)
    └─ isResponse=true → ResumeWaiting(100, resp)
         ├─ responseMap_[100] = resp
         └─ handle.resume()              // 协程从 co_await 处继续
              └─ await_resume() 从 responseMap_ 取出 resp 返回
```

### 5. 设计要点

- **session 机制**：`nextSessionId_` 单调递增，`waitMap_`(session→handle) + `responseMap_`(session→msg) 双表。`ResumeWaiting` 先存响应再 `resume`，保证 `await_resume` 拿得到值
- **协程总是在 Actor 的 worker 线程恢复**：因为响应消息走 `Send()` → 就绪队列 → worker → `ProcessOne` → `ResumeWaiting`。一个 Actor 同一时刻只可能被一个 worker 处理（`scheduled_` 保证），所以协程内部的状态（`waitMap_`, `responseMap_`, `nextSessionId_`）**不需要加锁**
- **协程帧泄漏防护**：`DestroyAllCoroutines()` 析构或 Stop 时遍历 `waitMap_` 把未完成的 `coroutine_handle` 显式 `destroy()`
- **Skynet 对标**：`Call` ≈ `skynet.call`、`Sleep` ≈ `skynet.sleep`、`Respond` ≈ `skynet.ret`、`ClusterCall` ≈ `cluster.call`

## 五、Reactor 与 Actor 的协作

### 职责分工

| 模型 | 在本框架中的实现 | 职责 | 线程数 |
|---|---|---|---|
| **Reactor** | `EventLoop` + `Poller`(epoll) | I/O 多路复用、读写网络数据 | **1 个** I/O 线程 |
| **Actor** | `ActorSystem` + `Actor` | 业务逻辑、消息串行处理 | **N 个** worker 线程 |

**关键桥梁**：`fd ↔ actorId` 映射 + `ActorMessage`

### 核心思想

> **Reactor 是"网络数据搬运工"，Actor 是"业务处理流水线"，二者通过 `ActorMessage` 和 `fd↔actorId` 映射对接——Reactor 把 socket 字节翻译成 Actor 消息投递进去，Actor 处理完再回调 Reactor 的发送接口把字节送回 socket。**

### 与"经典单 Reactor + 线程池"的区别

| 维度 | 经典 Reactor+ThreadPool | 本框架 Reactor+Actor |
|---|---|---|
| 业务并发单位 | 任意函数（线程池任务） | Actor（带状态） |
| 状态共享 | 共享内存 + 锁 | 消息传递（无锁） |
| 同一连接的请求顺序 | 需要业务自己保证 | 同一 fd→同一 Actor，**天然有序** |
| 异步等待 | 回调/Future | **协程 co_await**（同步写法） |
| 故障隔离 | 一个任务崩溃可能影响整个池 | 单个 Actor 异常不影响别人 |

## 六、EventLoop 单线程的 I/O 压力

### 单线程 Reactor 能力上限

| 场景 | 单线程 epoll 大致能力 |
|---|---|
| 长连接 + 心跳为主（如 IM） | 10万 ~ 100万 fd（C10K/C100K） |
| 短连接 + 简单回包 | 30万 ~ 80万 QPS |
| 中等业务（含解码 + 简单路由） | 10万 ~ 30万 QPS |
| 重业务（解析复杂协议） | 1万 ~ 10万 QPS |

### 关键优势：Reactor 极轻

EventLoop 线程**只做**：
- `epoll_wait`
- 查 fd→callback
- 调 `Connection::OnRead`/`OnWrite`

**业务逻辑（解析、计算、DB 查询）全部分发给 Actor 的 worker 线程池处理**。单线程只承担"搬字节"的活，能力上限就接近"纯 I/O 上限"——这就是 Reactor + Actor 这套架构的精髓。

### 适用判断

| 你的场景 | 建议 |
|---|---|
| 在写游戏服 / IM / API 网关 | 单 Reactor 够用，**别瞎优化** |
| 在做高频交易、CDN、推送系统 | 压测一下，**单核打到 60% 以上就考虑多 Reactor** |
| 不确定 | 先跑业务，用 `top -H` 看 EventLoop 线程的 CPU 占用 |

## 七、代码审查与问题清单

### 🔴 P0 正确性问题

#### 1. 跨线程 `Send()` 直接调 `epoll_ctl`，存在数据竞争
```cpp
void ConnectionBase::Send(...) {
    sendMQ_.push(...);
    loop_->GetPoller()->ModifyEvent(socket_, EPOLL_EVENTS_RW);  // ⚠️ 跨线程调用
}
```
worker 和 EventLoop 线程都改 epoll，可能丢失写事件。

#### 2. RemoveConnection 跨线程 UAF
EventLoop 线程在 `run()` 里**已经从 `firedEvents` 取出 fd**，**拷贝了回调 cb**，但还没执行 `cb(fd, events)`。此时 worker 线程调 `RemoveConnection(fd)` → delete Connection → 回到 EventLoop 线程执行 `cb(...)`，访问悬空指针。

| #13 | `Send` 没校验 nullptr/0 长度 |

### 核心设计点

#### 1. `RunInLoop` vs `QueueInLoop`

```cpp
RunInLoop(task):      在 loop 线程 → 立即同步执行
                      其他线程    → 入队 + 唤醒

QueueInLoop(task):    无论在哪个线程都入队，不立即执行
```

**关键**：`RemoveConnection` 必须用 `QueueInLoop`——即使是 loop 线程内调用（HandleRead 自删），也强制延迟到下一轮 `runPendingTasks`，避免在回调里删 this。

#### 2. `ModifyEventKeepCallback` 而不是普通 `ModifyEvent`

普通 `ModifyEvent(fd, events, cb)` 会重置回调。Send/HandleWrite 路径调用频繁，每次都拷贝并替换 `std::function` 是浪费——所以新增"只改 epoll 事件位、不动回调表"的接口。

#### 3. eventfd 唤醒

```cpp
wakeupFd_ = eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC);
poller_->AddEvent(wakeupFd_, EPOLLIN);
callbacks_[wakeupFd_] = [this](int, uint32_t){ handleWakeup(); };
```

- 跨线程要唤醒 loop：写 1 字节到 wakeupFd
- Stop 时也用 wakeup 让永久阻塞的 `Wait(-1)` 立刻返回
- 退出延迟从最坏 25ms 降到 ~微秒级

#### 4. 安全的连接删除时序

```
HandleRead 内调 RemoveConnection(fd)
   ↓
QueueInLoop 入队（不执行）
   ↓
HandleRead 返回 → cb 副本析构 → 控制权回到 EventLoop::run
   ↓
本轮事件处理完毕 → runPendingTasks() 执行 → 真正 delete Connection
```

**没有任何一行代码在 delete 后访问 this**。

## 九、关键机制详解

### 1. `loopThreadId_` 的作用

记录 EventLoop 工作线程 ID。配套 `IsInLoopThread()` 用于判断"当前调用是否在 loop 线程内"，决定 `RunInLoop` 走"同步直执行"还是"入队投递"。

赋值时机必须在 `run()` 里（loop 线程内）：
```cpp
void EventLoop::run(int timeout) {
    loopThreadId_ = std::this_thread::get_id();   // ← 在 loop 线程内自己记下来
    ...
}
```

### 2. `eventfd` 详解

**Linux 特有的系统调用**，创建一个**只用于线程/进程间通知**的特殊文件描述符。本质上是个**内核维护的 64 位无符号计数器**，配上一个 fd。

#### 参数解读

```cpp
wakeupFd_ = ::eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC);
```

- **`initval=0`**：初始计数器为 0，fd 不可读，loop 线程会在 epoll_wait 里阻塞
- **`EFD_NONBLOCK`**：非阻塞——read/write 不会卡死
- **`EFD_CLOEXEC`**：子进程 exec 时自动关闭这个 fd

#### 特性

1. 无系统调用入口的额外内核对象（比 pipe 更轻）
2. 原子写入（不需要用户态加锁）
3. **唤醒去重天然**：100 次 write 累加到 100，loop 一次 read 清空，**只触发 1 次 epoll 唤醒**
4. 不占网络栈
5. 天然与 epoll 配合

### 3. `wakeup()` / `handleWakeup()` 机制

**核心目的**：让阻塞中的 `epoll_wait` 强行叫醒。

```cpp
void EventLoop::wakeup() {
    uint64_t one = 1;
    ::write(wakeupFd_, &one, sizeof(one));    // 让 fd 可读
}

void EventLoop::handleWakeup() {
    uint64_t cnt = 0;
    ::read(wakeupFd_, &cnt, sizeof(cnt));     // 读掉计数器，复位
}
```

**门铃只负责"叫醒"，不负责"传达内容"**——内容靠"收件箱"（pendingTasks_）传。

### 4. RunInLoop 详解

**核心思路**：worker 不自己执行，而是**把"想做的事"打包成一个函数对象**，**塞给 loop 线程**，让 loop 线程**代替自己执行**。

```cpp
void EventLoop::RunInLoop(PendingTask&& task) {
    if (IsInLoopThread()) {        // ★ 关键判断
        task();                     // 同线程：立即执行
    } else {
        QueueInLoop(std::move(task));  // 跨线程：入队
    }
}

void EventLoop::QueueInLoop(PendingTask&& task) {
    {
        LockGuard lock(pendingLock_);
        pendingTasks_.emplace_back(std::move(task));   // ① 入队
    }
    if (!IsInLoopThread()) {
        wakeup();                                       // ② 按铃
    }
}
```

#### 加锁方案 vs RunInLoop

| 维度 | 加锁方案 | RunInLoop 方案 |
|---|---|---|
| **思路** | "并发访问要互斥" | "把跨线程调用转成单线程顺序执行" |
| **解决的问题** | 数据竞争 | 数据竞争 + 因果顺序 + 内核 race + 自删 UAF + 同步死锁 |
| **临界区长度** | 含系统调用，长 | 只有 push，短 |
| **可扩展性** | worker 越多锁竞争越严重 | 任务批处理，worker 越多越能摊薄 |
| **代码复杂度** | 看起来简单，但坑多 | 多一层抽象，但坑都被吃掉 |

#### 加锁不能完全解决的 4 个真问题

1. epoll_ctl 和 epoll_wait 的内核 race（用户态锁管不到）
2. ModifyEvent 语义先后错乱（锁只保证不并发，不调整顺序）
3. HandleRead 自删的 UAF（单线程内的同步调用，锁解决不了）
4. 跨线程同步等待 → 死锁

### 5. `runPendingTasks` 顺序

```cpp
while (!stop_) {
    epoll_wait(...);
    for (events) cb(...);     // Step 1: 处理 fd 事件
    runPendingTasks();         // Step 2: 处理跨线程任务
}
```

**`cb` 是因，`task` 是果**——业务回调（HandleRead/HandleWrite）可能产生跨线程任务，而跨线程任务不会反过来产生即时的业务回调。所以**让"因"先跑、"果"后跑**，本轮把整个因果链消化干净，是最自然也最高效的选择。

### 6. epoll 事件状态机（EPOLLIN / EPOLLOUT）

#### EPOLLOUT 是个"火"
只要监听它且 socket 可写就会反复触发 → CPU 100% 空转。

**正确做法**：只在"有数据要发但发不完"时才监听 EPOLLOUT，发完立刻取消监听。

#### 三个时机

| 时机 | 操作 | 类比 |
|---|---|---|
| Send | 加 EPOLLOUT | "我有件要发，闹钟一响就发" |
| HandleRead | 不动 | 收件跟发件无关，**别动闹钟** |
| HandleWrite 全发完 | 取消 EPOLLOUT | "件全发完了，**关闹钟**！不然它一直响" |
| HandleWrite 没发完 | 保持 EPOLLOUT | "缓冲区满了，等会还要继续发，**闹钟先留着**" |

### 7. ModifyEventKeepCallback 与 ModifyEvent 的区别

| 接口 | 行为 | 适用场景 |
|---|---|---|
| `ModifyEvent(fd, events, cb)` | 改监听位 + 替换回调 | 新注册 |
| `ModifyEventKeepCallback(fd, events)` | 只改监听位 | 运行中状态切换 |

`Send` / `HandleWrite` 高频路径只想做后者，强行用前者要么 API 调不通、要么白白构造 lambda。

### 8. RunInLoop 在 ModifyEventKeepCallback 内的必要性

去掉 RunInLoop 直接调 `poller_->ModifyEvent`，会**回到优化前的所有并发 bug**：
- worker 和 loop 同时改 callbacks_/poller_
- ModifyEvent 语义错乱（Send 后被 HandleWrite 覆盖）

**`RunInLoop` 不是装饰，它是整个并发安全模型的入口闸门**。

## 十、潜在 race 与彻底修复

### Race 描述

```
Loop 线程                              Worker 线程
═══════════                            ═══════════

cb(fd, EPOLLOUT) → HandleWrite 开始
  while (!sendMQ_.empty()) { ... }
  while 退出（sendMQ_ 空）
  
  【★ 此时 worker 抢插 ★】
                                       Send("new_data")
                                         sendMQ_.push("new_data")
                                         ModifyEventKeepCallback(RW)
                                            → IsInLoopThread()=false
                                            → QueueInLoop:
                                                pendingTasks_.push(task_RW)
                                                
  ModifyEventKeepCallback(R)
     → IsInLoopThread()=true
     → 同步执行 poller_->ModifyEvent(fd, R)
     ★ epoll 状态 = R ★
```

虽然在当前代码下 task_RW 仍会在 `runPendingTasks` 兜底覆盖回 RW，但代码**很脆弱**——依赖 3 条不变量：
1. HandleWrite 必须在 loop 线程执行
2. ModifyEvent(R) 必须只来自 HandleWrite
3. runPendingTasks 必须在 cb 之后执行

### 修复方案

把 `Send` 中的 `push + ModifyEvent` 整体投递到 loop 线程：

```cpp
void ConnectionBase::Send(const char* pData, int nLen) {
    if (pData == nullptr || nLen <= 0 || socket_ < 0) return;

    int fd = socket_;
    std::string data(pData, nLen);
    loop_->RunInLoop([this, fd, data = std::move(data)]() mutable {
        // 此时已在 loop 线程，与 HandleWrite 互斥
        sendMQ_.push(std::move(data));
        loop_->ModifyEventKeepCallback(fd, EPOLL_EVENTS_RW);
    });
}
```

`HandleRead` / `HandleWrite` 加 `assert` 防御：

```cpp
assert(loop_->IsInLoopThread() && "HandleRead must be called in loop thread");
assert(loop_->IsInLoopThread() && "HandleWrite must be called in loop thread");
```

### 新模型下的不变量

| 操作 | 线程 |
|---|---|
| `sendMQ_.push` | **loop 线程**（之前 worker 线程） |
| `sendMQ_.pop` | loop 线程 |
| `ModifyEvent(RW)` from Send | loop 线程 sync |
| `ModifyEvent(R)` from HandleWrite 收尾 | loop 线程 sync |

**结果**：sendMQ_ 完全单线程访问，所有 ModifyEvent 都同步顺序执行，**race 不可能再发生**。

### 性能影响

每次 `Send` 多了：
- 1 次 `RunInLoop` 调用（lambda 构造 + 移动）
- 1 次 pendingLock_ 加锁 + push
- 1 次 eventfd write 系统调用（~100ns）

总开销约 **1~2 微秒**，对绝大多数业务可忽略。

### 关于 std::string 拷贝

异步投递必然要深拷贝（pData 是栈指针，task 异步执行时早失效）。但**优化前后拷贝次数都是 1 次**，没有增加。真正额外的开销在 lambda 构造和 eventfd（~1-2μs），但保证正确性完全值得。

## 十一、与 muduo 的性能对比

### 整体架构对比

| 维度 | net_actor | muduo |
|---|---|---|
| **Reactor 数量** | 1 个 EventLoop | 主从 Reactor（1 主 + N 从） |
| **业务执行模型** | Actor 模型 + 协程 | 直接在 Reactor 线程跑回调 + 业务线程池 |
| **跨线程通知** | eventfd + RunInLoop | eventfd + runInLoop |
| **TimerQueue** | 独立线程 + 最小堆 | timerfd + 红黑树，归属于 EventLoop |
| **Buffer** | `std::string` 队列 + lastMsgCache_ | 自实现 `muduo::net::Buffer` |
| **fd→callback 映射** | `unordered_map<int, function>` | `Channel` 对象绑定，无 map 查找 |

### 单连接吞吐对比

模拟"每秒 10 万次 Send，每次 64B 小包"：

单次 Send 总差距约 **500ns**，10 万 QPS 下约 50ms/秒 CPU = 5% 一个核。**有差距，但不大**。

### 多连接 / 高并发对比

这是差距最明显的地方：
- **muduo**：N 个 SubReactor 分担连接，**充分利用多核**
- **net_actor**：只有 1 个 EventLoop 线程，**单核瓶颈**

当 EventLoop 核心打满时，muduo 还能加 SubReactor 扩展，net_actor 只能优化代码或上多 EventLoop 改造。

### 内存分配密度对比

| 场景 | net_actor | muduo |
|---|---|---|
| 1KB 包 × 10万 QPS | 10万次 malloc/free | ~0 次（Buffer 复用） |
| 64B 包 × 10万 QPS | SSO，~0 次 | ~0 次 |
| 16KB 包 × 10万 QPS | 10万次 malloc/free + memmove | Buffer 内移动 |

### 协程开销 vs 业务线程

net_actor **集成了协程**（Skynet 风格），muduo 没有。

**优势**：
- 业务代码可写同步代码风格
- 无需 Future/Callback 嵌套
- 心智成本低

### 性能差距百分比估计

**单 EventLoop 场景**（C100K 长连接 + 中等 QPS）：

| 测试维度 | net_actor 相对 muduo |
|---|---|
| 吞吐（小包高频） | ~85-90% |
| 吞吐（中包高频） | ~70-80%（malloc 拖累） |
| 延迟（P50） | 接近（+几微秒） |
| 延迟（P99） | net_actor 稍差 |
| 内存占用 | net_actor 稍高 |
| 多核扩展 | net_actor 大幅落后 |

### 拉近差距的优化优先级

| 优化项 | 难度 | 预期收益 |
|---|---|---|
| **多 EventLoop（主从 Reactor）** | 中 | **巨大**——多核横向扩展 |
| **Send fast-path 直发** | 低 | 大——loop 线程内 Send 无积压时直接 write，零拷贝 |
| **引入 Buffer 类替代 std::string** | 中 | 大——中大包高 QPS 场景 |
| **Channel 化（fd→对象指针）** | 中 | 中——避免每次事件 map 查找 |
| **TimerManager 改 timerfd 集成** | 低 | 小——少一个线程，省同步 |
| **回调用 shared_ptr<function>** | 低 | 小——优化 callbacks_ 拷贝 |
| **HandleRead 用 readv + 多 buffer** | 中 | 中——大量 ET 触发场景 |

### 最终定位

| 你的目标 | 推荐 |
|---|---|
| 写 IM、游戏服、推送、API 网关 | **net_actor**（业务复杂，协程救命） |
| 写 HTTP 高吞吐反向代理 | **muduo**（纯 I/O，多 Reactor 优势明显） |
| 学习 C++ 网络框架 | 两个都看，net_actor 的协程更前沿 |
| 做高性能存储中间件 | **muduo**（极致 I/O 吞吐） |
| 上百万长连接的实时业务 | **muduo + 自实现协程**，或 net_actor 加多 Reactor |

**两者不是同类**：
- **muduo 是纯 Reactor 框架**，性能极致
- **net_actor 是 Reactor + Actor + 协程全栈框架**，业务侧效率高一个量级

形象比喻：

> **muduo 是 F1 赛车**——只有座椅 + 引擎，跑得飞快，但开起来累。
> **net_actor 是性能尚可的 SUV**——有空调、有导航、有协程、有 Actor，开起来舒服，速度稍慢但综合体验好。
