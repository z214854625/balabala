## 一、整体架构与代码导读

整个框架是一个 **Actor 模型 + C++20 协程** 的网络服务框架，对标 Skynet 的服务协程模型。

### 线程模型

```
┌─────────────────┐   ┌──────────────────────────────────┐
│  EventLoop线程  │   │      ActorSystem Worker线程池      │
│  (单线程 epoll) │   │   (workerLoop × N，处理业务)        │
│   I/O 读写      │──▶│   ProcessOne → OnMessage → 协程    │
└─────────────────┘   └──────────────────────────────────┘
        ▲                          ▲
        │                          │
┌────────────────┐         ┌─────────────────┐
│ TimerManager   │         │ ClusterTransport│
│ 独立线程+最小堆 │         │ (跨进程TCP通信) │
└────────────────┘         └─────────────────┘
```

### 核心组件

- **EventLoop**：1 个 epoll 线程，承担所有 I/O；读到数据后投递给 Actor
- **ActorSystem**：N 个 worker 线程从就绪队列拉 Actor 处理消息
- **Actor**：拥有独立邮箱，消息串行处理，原 `CoroutineActor` 已合并进来
- **TimerManager**：单独线程 + 最小堆，处理 `Sleep`/`SetTimeout`/`SetInterval`
- **ClusterProxy / IClusterTransport**：跨进程消息透传
- **EventLoopThreadPool**：[2026.5 新增] 主从 Reactor 模式下的 SubReactor 池
- **Buffer**：[2026.5 新增] muduo 风格双游标发送缓冲区

## 三、Actor 模式核心逻辑

### 1. 邮箱（双队列，P3 优化）

`Actor` 内部维护两个 `SpinLockQueue`：
- `priorityMailbox_`：高优先级
- `normalMailbox_`：普通

`PushMessage` 根据 `msg.priority` 路由，`ProcessOne` 优先弹出高优先级。

### 2. 调度（ActorSystem）

每个 Actor 有一个原子标记 `scheduled_`，避免就绪队列中重复出现。

`Send()` 流程：取出 Actor → `PushMessage` → CAS 设置 `scheduled_` → 入就绪队列 → `cv_.notify_one()`。

`workerLoop()`：
1. 从就绪队列 `pop` 一个 actorId
2. 批量处理至多 64 条消息（防止饥饿）
3. 用 `try/catch` 包裹，单条消息异常不影响 worker 存活（P0）
4. 处理完后，邮箱非空则重新入队，邮箱空则清 `scheduled_` 并做**双重检查**

#### `scheduled_.store(false)` 与双重检查的必要性

如果不写 `store(false)`：worker 处理完后退出，但 `scheduled_` 仍为 true。后续 Send 触发 CAS 失败 → **不会入就绪队列** → Actor 永远不会被处理 → "丢失唤醒"bug。

双重检查解决了 `IsMailboxEmpty` 检查与 `store(false)` 之间的窗口竞态。

### 3. 消息分发（关键，`Actor::OnMessage`）

```cpp
if (msg.isResponse && msg.sessionId > 0) {
    ResumeWaiting(msg.sessionId, std::move(msg));  // 唤醒挂起的协程
} else {
    OnCoroutineMessage(std::move(msg));             // 新消息 → 启动新协程
}
```

### 4. 其他能力

- **fd→actorId 绑定**：网络数据按 fd 路由到对应 Actor
- **命名服务**：`RegisterName`/`FindActor`/`SendByName`（P1）
- **Link 监控**：`LinkActor` 注册 watcher，被监控 Actor 注销时 `notifyActorDown` 发送 `ActorDown` 消息（P2）
- **跨进程集群**：`SendToRemote` 走 `IClusterTransport`，封装为 `ClusterPacket`
- **优雅关停**：Stop 五阶段——停定时器 → 停 worker → 排空邮箱 → 警告未处理消息 → 清名字/Link 映射
- **指标**：`ActorMetrics`（处理数、累计/最大耗时、最大邮箱、优先级数）

### `workerLoop` 中的 try/catch 性能影响

C++ 现代异常实现是 **table-based zero-cost exception**：
- **不抛异常时**：几乎为 0 成本（编译期登记）
- **抛异常时**：贵，但属于"已经出错"场景

`workerLoop` 的 try 包了一整批消息（≤64 条），不是每条一个 try——**这是教科书级的合理用法**。

## 四、协程逻辑（Skynet 风格服务协程）

### 1. 返回类型 `ActorTask`

```cpp
struct promise_type {
    std::suspend_never initial_suspend();   // 立刻执行
    std::suspend_never final_suspend();     // 完成自动销毁帧
    void return_void(); ...
};
```

**Fire-and-forget**：调用方不持有 `coroutine_handle`，协程帧生命周期由挂起点和 `final_suspend` 管理。

### 2. 协程入口

`OnCoroutineMessage(ActorMessage msg)` 是用户重写的虚函数，**参数按值传递**——因为协程可能挂起，原 `ProcessOne()` 的栈引用会失效。

### 3. 三种 Awaiter

| Awaiter | 触发 | 挂起时 | 何时恢复 |
|---|---|---|---|
| `CallAwaiter` | `co_await Call(id, msg)` | AllocSession + StoreWaiting + SendToActor | 目标 Actor `Respond` 回发 isResponse=true 的消息 → `OnMessage` → `ResumeWaiting` |
| `ClusterCallAwaiter` | `co_await ClusterCall(node, name, msg)` | 同上，但用 `SendToRemote` | 远端 `RespondRemote` → TCP 返回 → ClusterGatewayActor 解码 → `SendByName` 路由 → `ResumeWaiting` |
| `SleepAwaiter` | `co_await Sleep(ms)` | 注册等待 + `TimerManager.SetTimeout` 投递唤醒消息 | 定时器到期 → `ResumeWaiting` |

### 4. 协程的"挂起-恢复"全流程

```
Actor A 在 worker 线程中：
  OnCoroutineMessage(msg)
    └─ co_await Call(B, req)              // CallAwaiter
         ├─ AllocSession → 100
         ├─ waitMap_[100] = handle        // StoreWaiting
         ├─ Send(B, req{sessionId=100})
         └─ 协程挂起 → worker线程返回 → 处理其他Actor

… Actor B 在另一个 worker 线程：
  OnCoroutineMessage(req)
    └─ RespondToCall(req, resp)
         └─ resp.isResponse=true, sessionId=100 → Send(A, resp)

… Actor A 再次被调度：
  ProcessOne → OnMessage(resp)
    └─ isResponse=true → ResumeWaiting(100, resp)
         ├─ responseMap_[100] = resp
         └─ handle.resume()              // 协程从 co_await 处继续
              └─ await_resume() 从 responseMap_ 取出 resp 返回
```

### 5. 设计要点

- **session 机制**：`nextSessionId_` 单调递增，`waitMap_`(session→handle) + `responseMap_`(session→msg) 双表
- **协程总是在 Actor 的 worker 线程恢复**：一个 Actor 同一时刻只可能被一个 worker 处理（`scheduled_` 保证），所以协程内部的状态**不需要加锁**
- **协程帧泄漏防护**：`DestroyAllCoroutines()` 析构或 Stop 时遍历 `waitMap_` 把未完成的 `coroutine_handle` 显式 `destroy()`
- **Skynet 对标**：`Call` ≈ `skynet.call`、`Sleep` ≈ `skynet.sleep`、`Respond` ≈ `skynet.ret`、`ClusterCall` ≈ `cluster.call`

## 五、Reactor 与 Actor 的协作

### 职责分工

| 模型 | 在本框架中的实现 | 职责 | 线程数 |
|---|---|---|---|
| **Reactor** | `EventLoop` + `Poller`(epoll) | I/O 多路复用、读写网络数据 | **1 个** I/O 线程（单 Reactor）或主+N 个 SubReactor |
| **Actor** | `ActorSystem` + `Actor` | 业务逻辑、消息串行处理 | **N 个** worker 线程 |

**关键桥梁**：`fd ↔ actorId` 映射 + `ActorMessage`

### 整体架构图

```
┌────────────────────────────────────────────────────────────────────┐
│                          外部网络客户端                              │
│                            (TCP连接)                                 │
└──────────────────────────────────┬─────────────────────────────────┘
                                   │ socket fd
                                   ▼
╔════════════════════════════════════════════════════════════════════╗
║                   REACTOR 层（1个 EventLoop 线程）                   ║
║  Poller (epoll_wait)  ←  监听所有 fd 的 EPOLLIN/EPOLLOUT             ║
║         ↓ fd 事件                                                    ║
║  EventLoop::run() 分发回调                                            ║
║  ├── Acceptor::OnAccept       (新连接 → 创建 Connection)              ║
║  ├── Connection::OnRead       (读数据到 buffer)                       ║
║  └── Connection::OnWrite      (发送 pending 数据)                     ║
║         ↓ ★ I/O → Actor ★                                            ║
║       1. GetActorIdByFd(fd) 查 fd→actorId                            ║
║       2. 构造 ActorMessage                                            ║
║       3. ActorSystem::Send()                                          ║
╚══════════════════════════════════════════════════════════════════════╝
                    │ ActorMessage 投递
                    ▼
║              ACTOR 层（ActorSystem，N 个 worker 线程）                ║
║  Worker 线程 从 readyQueue_ 取 actorId                                ║
║         ↓                                                             ║
║  Actor::ProcessOne()                                                  ║
║   → OnMessage(msg)                                                    ║
║     ├─ isResponse?  → 恢复协程                                         ║
║     └─ 否          → OnCoroutineMessage(msg)                          ║
║                       ├─ 业务逻辑                                      ║
║                       ├─ co_await Call(...)                          ║
║                       └─ SendToNetwork(fd, data) ──┐                  ║
║                                                    │                  ║
║       ★ Actor → I/O ★                              │                  ║
║       通过 EventLoop->GetConnection(fd)            │                  ║
║       → Connection::Send() ◀──────────────────────┘                  ║
║       （回到 Reactor 的发送通路）                                       ║
```

### 核心思想

> **Reactor 是"网络数据搬运工"，Actor 是"业务处理流水线"**，二者通过 `ActorMessage` 和 `fd↔actorId` 映射对接——Reactor 把 socket 字节翻译成 Actor 消息投递进去，Actor 处理完再回调 Reactor 的发送接口把字节送回 socket。

## 六、EventLoop 单线程的 I/O 压力

### 单线程 Reactor 能力上限

| 场景 | 单线程 epoll 大致能力 |
|---|---|
| 长连接 + 心跳为主（如 IM） | 10万 ~ 100万 fd |
| 短连接 + 简单回包 | 30万 ~ 80万 QPS |
| 中等业务（含解码 + 简单路由） | 10万 ~ 30万 QPS |
| 重业务（解析复杂协议） | 1万 ~ 10万 QPS |

### 关键优势：Reactor 极轻

EventLoop 线程**只做** `epoll_wait` + 查 callback + 调 `Connection::OnRead`/`OnWrite`。业务全部分发给 Actor worker 线程池处理。

### 适用判断

| 场景 | 建议 |
|---|---|
| 游戏服 / IM / API 网关 | 单 Reactor 够用 |
| 高频交易、CDN、推送系统 | 压测单核 60%+ 考虑多 Reactor |

## 八、P2 及以上问题修复

### 改动文件总览

| 文件 | 主要变化 |
|---|---|
| `EventLoop.h/.cc` | 新增 RunInLoop/QueueInLoop/Stop/IsInLoopThread/ModifyEventKeepCallback；eventfd 唤醒 + 跨线程任务队列 |
| `ConnectionBase.cc` | Send 加空指针校验，改走 ModifyEventKeepCallback；HandleRead 移除 memset；删除调试日志 |
| `Connector.cc` | 替换直调 poller_->ModifyEvent |

### 核心设计点

#### 1. `RunInLoop` vs `QueueInLoop`

```cpp
RunInLoop(task):      在 loop 线程 → 立即同步执行
                      其他线程    → 入队 + 唤醒

QueueInLoop(task):    无论在哪个线程都入队，不立即执行
```

`RemoveConnection` 必须用 `QueueInLoop`——即使在 HandleRead 内自删，也强制延迟到下一轮 `runPendingTasks`，避免在回调里删 this。

#### 2. `ModifyEventKeepCallback` 而不是普通 `ModifyEvent`

Send/HandleWrite 路径调用频繁，每次都拷贝并替换 `std::function` 是浪费——新增"只改 epoll 事件位、不动回调表"的接口。

#### 3. eventfd 唤醒

```cpp
wakeupFd_ = eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC);
poller_->AddEvent(wakeupFd_, EPOLLIN);
callbacks_[wakeupFd_] = [this](int, uint32_t){ handleWakeup(); };
```

退出延迟从最坏 25ms 降到 ~微秒级。

## 九、关键机制详解

### 1. `loopThreadId_` 的作用

记录 EventLoop 工作线程 ID。配套 `IsInLoopThread()` 用于判断"当前调用是否在 loop 线程内"，决定 `RunInLoop` 走"同步直执行"还是"入队投递"。

### 2. `eventfd` 详解

**Linux 特有的系统调用**，本质上是个**内核维护的 64 位无符号计数器**，配上一个 fd。

#### 特性
1. 无系统调用入口的额外内核对象（比 pipe 更轻）
2. 原子写入（不需要用户态加锁）
3. **唤醒去重天然**：100 次 write 累加到 100，loop 一次 read 清空，**只触发 1 次 epoll 唤醒**
4. 不占网络栈
5. 天然与 epoll 配合

### 3. `wakeup()` / `handleWakeup()` 机制

**核心目的**：让阻塞中的 `epoll_wait` 强行叫醒。

- `wakeup()`：写 1 字节到 wakeupFd_，让 fd 可读
- `handleWakeup()`：读掉计数器，清除可读事件

**门铃只负责"叫醒"，不负责"传达内容"**——内容靠"收件箱"（pendingTasks_）传。

### 4. RunInLoop 详解

```cpp
void EventLoop::RunInLoop(PendingTask&& task) {
    if (IsInLoopThread()) {        // ★ 关键判断
        task();                     // 同线程：立即执行
    } else {
        QueueInLoop(std::move(task));  // 跨线程：入队
    }
}
```

#### 加锁方案 vs RunInLoop

| 维度 | 加锁方案 | RunInLoop 方案 |
|---|---|---|
| **思路** | "并发访问要互斥" | "把跨线程调用转成单线程顺序执行" |
| **解决的问题** | 数据竞争 | 数据竞争 + 因果顺序 + 内核 race + 自删 UAF + 同步死锁 |
| **临界区长度** | 含系统调用，长 | 只有 push，短 |
| **可扩展性** | worker 越多锁竞争越严重 | 任务批处理 |

### 5. `runPendingTasks` 顺序

```cpp
while (!stop_) {
    epoll_wait(...);
    for (events) cb(...);     // Step 1: 处理 fd 事件
    runPendingTasks();         // Step 2: 处理跨线程任务
}
```

**`cb` 是因，`task` 是果**——让"因"先跑、"果"后跑，本轮把整个因果链消化干净。

### 6. epoll 事件状态机（EPOLLIN / EPOLLOUT）

**EPOLLOUT 是个"火"**：只要监听它且 socket 可写就会反复触发 → CPU 100% 空转。

| 时机 | 操作 | 类比 |
|---|---|---|
| Send | 加 EPOLLOUT | "我有件要发，闹钟一响就发" |
| HandleRead | 不动 | "别动闹钟" |
| HandleWrite 全发完 | 取消 EPOLLOUT | "件全发完了，**关闹钟**" |
| HandleWrite 没发完 | 保持 EPOLLOUT | "缓冲区满了，闹钟先留着" |

### 7. ModifyEventKeepCallback 内部必须用 RunInLoop

去掉 RunInLoop 直接调 `poller_->ModifyEvent`，会**回到优化前的所有并发 bug**。`RunInLoop` 是整个并发安全模型的入口闸门。

## 十、潜在 race 与彻底修复

### Race 描述

worker push 后 queue task_RW，loop HandleWrite 看到空队列后 sync ModifyEvent(R) → 最终状态 R 但 sendMQ_ 已有数据 → 卡死。

### 修复方案

把 `Send` 中的 `push + ModifyEvent` 整体投递到 loop 线程：

```cpp
void ConnectionBase::Send(const char* pData, int nLen) {
    if (pData == nullptr || nLen <= 0 || socket_ < 0) return;

    int fd = socket_;
    std::string data(pData, nLen);
    loop_->RunInLoop([this, fd, data = std::move(data)]() mutable {
        outputBuffer_.Append(data);
        loop_->ModifyEventKeepCallback(fd, EPOLL_EVENTS_RW);
    });
}
```

`HandleRead` / `HandleWrite` 加 `assert` 防御：

```cpp
assert(loop_->IsInLoopThread() && "HandleRead must be called in loop thread");
assert(loop_->IsInLoopThread() && "HandleWrite must be called in loop thread");
```

### 新模型下的不变量

| 操作 | 线程 |
|---|---|
| `outputBuffer_.Append` | **loop 线程**（之前 worker 线程） |
| `Buffer.Retrieve` | loop 线程 |
| `ModifyEvent(RW)` from Send | loop 线程 sync |
| `ModifyEvent(R)` from HandleWrite 收尾 | loop 线程 sync |

**race 不可能再发生**。

## 十一、Buffer 类改造

### 设计：muduo 风格双游标

```
+---------+----------------+----------------+
| prepend |    readable    |    writable    |
+---------+----------------+----------------+
0    readerIndex_     writerIndex_      capacity()
```

| 区域 | 范围 | 用途 |
|---|---|---|
| **prepend** | 0 ~ readerIndex_ | 已发送区，回收做扩容缓冲 |
| **readable** | readerIndex_ ~ writerIndex_ | 等待发送的数据 |
| **writable** | writerIndex_ ~ size | 剩余可写空间 |

### 关键操作

| 操作 | 复杂度 | 是否分配 |
|---|---|---|
| `Append(data, len)` | O(len) memcpy | 仅当容量不够时扩容 |
| `Peek()` | O(1) 返指针 | 否 |
| `Retrieve(n)` | O(1) 移指针 | 否 |
| `MakeSpace(len)` | 偶尔 O(readable) memmove | 仅扩容时 vector resize |

### 性能优势

| 场景 | 改造前（sendMQ_+lastMsgCache_） | 改造后（Buffer） |
|---|---|---|
| 高频 Send malloc/秒 | 10万次（每条 string） | ~0 次（buffer 复用） |
| HandleWrite 写出 | pop string，逐条 write | 单次大块 write |
| 半包路径 | 构造 lastMsgCache_ 字符串 | 0 次（移指针） |

**10 条小包**：原方案 10 次 write 系统调用 → 新方案 **1 次 write**（聚合发送）。

### 初始容量

`kInitialSize = 64 * 1024`（64KB）—— 适合中包场景。

## 十二、Send fast-path 优化

### 触发条件

```cpp
if (IsInLoopThread() && outputBuffer_.Empty() && CanWriteDirectly()) {
    // Fast-path：直接 write socket，零拷贝零分配
    ...
}
```

**三个条件**：
1. 当前在 loop 线程
2. `outputBuffer_` 为空（无积压）
3. `CanWriteDirectly()` 为 true（Connector 在 connecting_ 时为 false）

### Fast-path vs Slow-path

| 路径 | 流程 | 开销 |
|---|---|---|
| **Fast-path** | 直接 write，写完即返回 | 零 string 构造、零 task 入队、零 wakeup |
| **Slow-path** | RunInLoop 投递 task | 1 次 string 构造 + 1 次 task + 1 次 eventfd |

### 适用场景

loop 线程内业务（典型：HandleRead 后立刻回包）能享受 fast-path 收益。

跨线程 Send（worker 线程）仍走 slow-path，但二次尝试 direct write（在 loop 线程内）。

## 十三、多 EventLoop 主从 Reactor

### 改动总览

| 文件 | 状态 | 改动 |
|---|---|---|
| **EventLoopThreadPool.h** | 🆕 新增 | SubReactor 池：SetThreadNum/Start/Stop/GetNextLoop |
| **ActorSystem.h/.cc** | 改 | 新增 `BindFdToActor(fd, actorId, loop)` 重载 + `GetEventLoopByFd(fd)`；维护 `fdToLoop_` 映射 |
| **Actor.cc** | 改 | `SendToNetwork` 改为按 fd 查 loop |
| **Acceptor.h/.cc** | 改 | 新增 `SetThreadPool`，HandleAccept 按 Round-Robin 分配 sub loop |
| **TcpServer.h/.cc** | 改 | `Start(port, subReactorNum=0, workerCount=4)` 默认参数 |

### 架构图

```
┌──────────────────────────────────────────────────┐
│  Main EventLoop (loop_)                          │
│  - Acceptor 在这里监听新连接                       │
└────────────────────┬─────────────────────────────┘
                     │ subReactorNum>0 时派发新连接
                     ▼
   ┌─────────────────────────────────────────────┐
   │  EventLoopThreadPool                         │
   │  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐    │
   │  │Sub 0 │  │Sub 1 │  │Sub 2 │  │Sub N │    │
   │  │ loop │  │ loop │  │ loop │  │ loop │    │
   │  └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘    │
   └─────┼─────────┼─────────┼─────────┼─────────┘
         │         │         │         │
         └─────────┴─────────┴─────────┘
                       │
                       ▼ ActorMessage 投递
       ┌─────────────────────────────────────┐
       │  ActorSystem (共享，所有 loop 共用)   │
       │  N 个 worker 线程跑 Actor 业务         │
       │  fd → EventLoop 映射                 │
       └─────────────────────────────────────┘
```

### 关键设计：完全兼容旧代码

```cpp
// 旧调用，完全不动：
TcpServer svr;
svr.Start(port);              // subReactorNum=0 → 走单 Reactor 老路径

// 启用主从 Reactor 只需改一行：
svr.Start(port, 4);           // 4 个 SubReactor
```

### Actor::SendToNetwork 自动适配

```cpp
auto* loop = system_->GetEventLoopByFd(fd);   // 自动找到 fd 所属 loop
```

- SubReactor 模式 → 返回 fd 所在的 sub loop
- 单 Reactor 模式 / 未绑定 → **回退主 loop**

**业务代码完全不需要改**。

### SubReactor 数量推荐

| CPU 核数 | 推荐 subReactorNum |
|---|---|
| 4 核 | 2-3 |
| 8 核 | 3-5 |
| 16 核+ | 6-8 |

## 十四、Gateway 路由 + 多业务 Actor

### 业界主流做法

游戏服多业务 Actor 路由几乎都是**协议头 + cmd 字段路由**：

```
+----------+----------+--------------+
| len(4B)  | cmd(2B)  | payload      |
+----------+----------+--------------+
```

**cmd 分段约定**：
```
0x0001 ~ 0x00FF  →  登录/账号模块
0x0100 ~ 0x01FF  →  场景模块（Scene）
0x0200 ~ 0x02FF  →  聊天模块（Chat）
0x0300 ~ 0x03FF  →  战斗模块（Battle）
```

### 五种路由模式对比

| 模式 | 适用场景 |
|---|---|
| **按 fd 绑定** | 每连接一个固定 Actor（游戏服每玩家一个 PlayerActor） |
| **按消息命令字** | HTTP 路由 / gRPC / 游戏服 cmd 路由 |
| **按会话身份** | 登录后改绑到 PlayerActor |
| **多阶段流转** | 登录前 Gateway → 登录后 PlayerActor |
| **一致性哈希** | Skynet 的 sharded 模式 |

### 推荐架构：单 Gateway + 多业务 Actor

```
   Acceptor
     │ Connected
     ▼
   GatewayActor
   - 按 fd 维护 inputBuf（解半包/粘包）
   - 按 cmd 路由
   ├── cmd ∈ 0x01XX → SceneActor
   └── cmd ∈ 0x02XX → ChatActor
                      │
                      ▼
              业务 Actor 并行处理
              ↓ SendToNetwork(fd, ...)
              写回客户端
```

### 关键实现

```cpp
class GatewayActor : public Actor {
    uint32_t sceneActorId;
    uint32_t chatActorId;
    std::unordered_map<int, std::string> fdInputBuf_;

    void onRecv(int fd, const std::string& data) {
        auto& buf = fdInputBuf_[fd];
        buf.append(data);
        while (buf.size() >= 4) {
            uint32_t bodyLen = ntohl(*(uint32_t*)buf.data());
            if (buf.size() < 4 + bodyLen) break;
            std::string fullFrame = buf.substr(0, 4 + bodyLen);
            buf.erase(0, 4 + bodyLen);
            routeFrame(fd, std::move(fullFrame));
        }
    }

    void routeFrame(int fd, std::string&& frame) {
        uint16_t cmd = parseCmd(frame);
        uint8_t module = (cmd >> 8) & 0xFF;
        ActorMessage forward(MsgType::NetworkRecv, GetActorId(), fd, std::move(frame));
        switch (module) {
            case 0x01: GetSystem()->Send(sceneActorId, std::move(forward)); break;
            case 0x02: GetSystem()->Send(chatActorId,  std::move(forward)); break;
        }
    }
};
```

### Gateway 不改绑 fd 的原因

- 所有 fd 都绑 GatewayActor，所有 NetworkRecv 都进 Gateway
- 同一 fd 的所有消息**保证顺序**（Actor 串行处理粘包流）
- Gateway 是唯一解协议的地方，**职责清晰**

### 转发用 Send，不改绑

```cpp
ActorMessage forward(MsgType::NetworkRecv, GetActorId(), fd, std::move(fullFrame));
sys->Send(sceneActorId, std::move(forward));
```

业务 Actor 拿到的 `forward.fd` 仍是原 fd，回包：

```cpp
SendToNetwork(msg.fd, ...);   // 自动通过 GetEventLoopByFd 找回 sub loop
```

**回包不经 Gateway**——直接走 EventLoop 的 SubReactor。

### 一个 Gateway 够吗？

**绝大多数场景下够用**。

#### 单 Gateway 处理能力

| 步骤 | 耗时 |
|---|---|
| 邮箱 push/pop | ~100 ns |
| string.append | ~50 ns |
| memcpy + ntohl 解头 | ~10 ns |
| substr + erase | ~200 ns |
| Send 给业务 Actor | ~200 ns |
| **总单帧** | **~600 ns ~ 1μs** |

**单 Gateway QPS 上限**：100万 ~ 150万 帧/秒。

#### 实际负载对比

| 场景 | QPS | 单 Gateway 占用 |
|---|---|---|
| 中小型游戏服（1万玩家） | 10-30万 | 10-20% |
| 战斗服（百局并发） | 几十万 | 25-40% |
| 大型 MMORPG（5万玩家） | 250万 | 不够，需拆 |

#### 什么时候需要多 Gateway

- **信号 1**：Gateway 邮箱持续积压 > 1000
- **信号 2**：Gateway worker 线程单核 100%
- **信号 3**：客户端延迟正常但响应慢

#### 拆分方式（按 fd 哈希）

```cpp
std::vector<uint32_t> gatewayIds;  // N 个 Gateway
int gwIdx = (fd >> 1) % gatewayIds.size();
actorSys->BindFdToActor(fd, gatewayIds[gwIdx], targetLoop);
```

**保证同一 fd 始终走同一 Gateway**——粘包缓冲不会拆分。

## 十五、与 muduo 的性能对比

### 整体架构对比

| 维度 | net_actor | muduo |
|---|---|---|
| **Reactor 数量** | 1 主 + N 从（已支持） | 主从 Reactor（1 主 + N 从） |
| **业务执行模型** | Actor 模型 + 协程 | 直接在 Reactor 线程跑回调 + 业务线程池 |
| **跨线程通知** | eventfd + RunInLoop | eventfd + runInLoop |
| **TimerQueue** | 独立线程 + 最小堆 | timerfd + 红黑树 |
| **Buffer** | muduo 风格双游标 Buffer | muduo 自实现 Buffer |
| **fd→callback 映射** | `unordered_map<int, function>` | `Channel` 对象绑定 |

### 性能差距百分比估计

**单 EventLoop 场景**（C100K 长连接 + 中等 QPS）：

| 测试维度 | net_actor 相对 muduo |
|---|---|
| 吞吐（小包高频） | ~85-90% |
| 吞吐（中包高频） | ~70-80% |
| 延迟（P50） | 接近 |
| 延迟（P99） | net_actor 稍差 |
| 内存占用 | net_actor 稍高 |
| **多核扩展** | **已支持主从 Reactor，接近 muduo** |

### 协程开销 vs 业务线程

net_actor **集成协程**，muduo 没有。

**优势**：
- 业务代码可写同步代码风格（`co_await Call(...)`）
- 无需 Future/Callback 嵌套
- 心智成本低

### 拉近差距的优化优先级

| 优化项 | 状态 | 预期收益 |
|---|---|---|
| **多 EventLoop（主从 Reactor）** | ✅ 已支持 | **巨大** |
| **Send fast-path 直发** | ✅ 已支持 | 大 |
| **引入 Buffer 类替代 std::string** | ✅ 已支持 | 大 |
| **Channel 化（fd→对象指针）** | 未做 | 中 |
| **TimerManager 改 timerfd 集成** | 评估后回退 | 小 |
| **回调用 shared_ptr<function>** | 未做 | 小 |
| **HandleRead 用 readv + 多 buffer** | 未做 | 中 |

### 最终定位

| 你的目标 | 推荐 |
|---|---|
| 写 IM、游戏服、推送、API 网关 | **net_actor** |
| 写 HTTP 高吞吐反向代理 | **muduo** |
| 学习 C++ 网络框架 | 两个都看 |
| 高性能存储中间件 | **muduo** |

**两者不是同类**：
- **muduo 是纯 Reactor 框架**，性能极致
- **net_actor 是 Reactor + Actor + 协程全栈框架**，业务侧效率高

形象比喻：

> **muduo 是 F1 赛车**——只有座椅 + 引擎，跑得飞快，但开起来累。
> **net_actor 是性能尚可的 SUV**——有空调、有导航、有协程、有 Actor，开起来舒服。
